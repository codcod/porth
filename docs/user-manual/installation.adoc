= Installation and running

== Requirements

* Python 3.13 or later (pinned in `.python-version`).
* https://github.com/astral-sh/uv[uv].
* A database: PostgreSQL 14 or later, or a local SQLite file (see <<Running on SQLite>>).
  `make db-up` starts a PostgreSQL in Docker (`compose.yaml`, user, password and database all
  `porth`, on port 5432). To use another host port, set `POSTGRES_PORT` and change the port in
  the `db` DSN to match (see <<Configuration>>).
* Network access from {product} to the upstream SMSC's SMPP port.

{product} installs its SMPP library, `smppai`, from its Git repository. The library is
imported as `smpp`.

== Install

[source,bash]
----
git clone git@github.com:codcod/porth.git
cd porth
make dev        # uv sync --dev
make db-up      # PostgreSQL in Docker
make migrate    # create porth's tables (schema porth)
----

`make migrate` runs `alembic upgrade head` against the PostgreSQL database in the `db`
setting (see <<Configuration>>). It is a one-off step: {product} never migrates PostgreSQL at
startup, so run it again before every start after an upgrade. It reads `db` from
`config/config.toml`. On SQLite skip both `make db-up` and `make migrate`: {product} creates
its tables at start (see <<Running on SQLite>>).

== Run

[source,bash]
----
make run        # bin/porth config/config.toml
----

The gateway listens on the HTTP address from its configuration (default `0.0.0.0:8080`).
It starts even when an SMSC is unreachable, and retries the bind every
`reconnect_delay`, 10 s by default (see <<The SMSC bind>>). It does not
start without its database: an unset `db`, an unreachable PostgreSQL or an unwritable SQLite
file stops it with an error.

Stop it with `SIGINT` (Ctrl+C) or `SIGTERM`. Shutdown first closes the HTTP API listener,
then stops the delivery workers, unbinds from the SMSC, and closes the Kannel listener.

== Try it without a carrier

The repository ships demos that run {product} in Docker against simulated SMSCs, with no
carrier and no install beyond Docker: a first send, authentication, routing and failover with
monitoring, and a reference Kannel to compare against. <<Demos>> describes each one.

== Container image

Every release publishes the image `ghcr.io/codcod/porth:<version>` (for example
`ghcr.io/codcod/porth:0.4.1`), and `ghcr.io/codcod/porth:latest` names the most recently
tagged release.
It runs on `linux/amd64` and `linux/arm64`, and needs no Python or uv on the host. It is a
distroless Python 3.13 runtime holding `bin/porth`, the default `config/`, the migrations and
`alembic.ini`. It exposes 8080 (HTTP API) and 13013 (Kannel), and runs as a non-root user.

The image's entrypoint is `python`, so the same image runs the gateway and the one-off
migrate step. Mount the deployment's configuration over the default:

[source,bash]
----
docker run --rm -v /etc/porth/config.toml:/opt/porth/config/config.toml:ro \
  ghcr.io/codcod/porth:<version> -m alembic upgrade head
docker run -d --restart unless-stopped -p 8080:8080 -p 13013:13013 \
  -v /etc/porth/config.toml:/opt/porth/config/config.toml:ro ghcr.io/codcod/porth:<version>
----

The migrate step reads `db` from the mounted file, as `make migrate` does. Run it before
every start after an upgrade. On SQLite there is no migrate step; see <<Running on SQLite>>
for the volume the database file needs.

The gateway logs to standard error. For a log shipper (Loki, ELK, Datadog), set
`log_format = "json"` for one JSON object per line (see <<Configuration>>).

To build the image from a clone instead, run `make docker-build`. It builds the same
`Dockerfile` into the local image `porth`, which takes the place of
`ghcr.io/codcod/porth:<version>` in the commands above.

== Running on SQLite

For a small deployment on one machine, {product} can keep its messages in a SQLite file
instead of PostgreSQL. Set `db` to the file, in SQLAlchemy's aiosqlite form:

[source,toml]
----
[porth]
db = "sqlite+aiosqlite:////var/lib/porth/porth.db"
----

It needs SQLite 3.35 or later in {product}'s Python (the container image has 3.46);
`python -c "import sqlite3; print(sqlite3.sqlite_version)"` prints it. An absolute path takes
four slashes after `sqlite+aiosqlite:`. With three, the path is
relative to the directory {product} starts in. The directory must exist and be writable;
{product} creates the file and its tables at the first start, so there is no `make migrate`
step (`alembic upgrade head` on a SQLite `db` exits with `SQLite: porth creates its schema at
startup; nothing to migrate`). An in-memory database (`:memory:`) is refused: it would lose
every message on a restart.

Next to the database {product} keeps `porth.db-wal` and `porth.db-shm` (SQLite's write-ahead
log) and `porth.db.lock`. Know what you give up before choosing SQLite:

* *One process.* {product} holds an exclusive lock on `<database file>.lock` while it runs,
  and a second {product} on the same file exits at start (see
  <<Running more than one instance>>). The database must be on a local disk: network file
  systems do not keep SQLite's or that lock's guarantees.
* *The disk is the only copy.* There is no standby. Back up with
  `sqlite3 porth.db ".backup /path/copy.db"`, which is safe while {product} runs; never copy
  the file with `cp` while {product} runs, since the copy can miss the write-ahead log.
* *The files hold every message.* {product} creates the database and its lock file readable
  by its own user only (mode 0600), and SQLite gives the write-ahead log the same mode. Keep
  the directory owned by {product}'s user with mode 0700, and protect a `.backup` copy the
  same way: it holds the same text, numbers and callback URLs.
* *One writer at a time.* Every database transaction takes SQLite's write lock, so writes are
  serialised, and the ceiling on messages per second is lower than on PostgreSQL. A
  transaction that waits more than 10 s for the lock fails as if the database were
  unreachable.
* *In a container* the database's directory must be a volume, or the messages go with the
  container:
+
[source,bash]
----
docker run -d --restart unless-stopped -p 8080:8080 -p 13013:13013 \
  -v /etc/porth/config.toml:/opt/porth/config/config.toml:ro \
  -v /var/lib/porth:/var/lib/porth ghcr.io/codcod/porth:<version>
----
+
The image runs as a non-root user, so that user must be able to write the volume's directory.

== What a restart keeps

Every message {product} accepts is written to its database before the API answers, and every
status change after that. After a stop or a crash, the next start:

* sends the messages that were not sent yet (`pending` or `queued`, including those waiting
  to retry), oldest first. A message already `sent` is not sent again.
* still matches later delivery receipts to their messages.
* makes again any Kannel `dlr-url` or HTTP `callback_url` call that was not finished, so a
  client can receive the same callback twice.

A message the SMSC accepted just before a crash, before {product} recorded it as `sent`, is
sent again. See <<Limitations>>.

== Running more than one instance

One {product} runs per database. At start it takes a PostgreSQL advisory lock and holds it
until it stops. A second {product} on the same database exits with an error before it sends
anything:

----
RuntimeError: Another porth already uses this database (advisory lock 482906109032 is held): stop it first
----

On SQLite the lock is an exclusive lock on `<database file>.lock`, which the operating system
frees when {product} exits, however it exits. The rest of this section is about PostgreSQL's
lock:

----
RuntimeError: Another porth already uses this database (/var/lib/porth/porth.db.lock is locked): stop it first
----

Every 10 s, {product} checks that its database session, and with it the lock, is still alive.
A check that gets no answer within 10 s fails too. After a database restart or a dropped
connection, it logs an error and stops, because another {product} may hold the lock by then.
It exits with code 0, or with code 1 if its shutdown is still running 30 s later. Either
way its supervisor must restart it on any exit (Docker `--restart always` or
`unless-stopped`, systemd `Restart=always`), not only on failure.

If {product}'s host disappears without closing its connection (a lost node, a network
partition), PostgreSQL keeps that session, and the lock, for up to 30 s after its last check
before ending it; until then a new {product} exits at start. To free the lock at once, run
this connected to {product}'s database:

[source,sql]
----
SELECT pg_terminate_backend(pid) FROM pg_locks
WHERE locktype = 'advisory' AND classid = 112 AND objid = 1869771880 AND objsubid = 1
  AND database = (SELECT oid FROM pg_database WHERE datname = current_database());
----

* Kubernetes: set the Deployment's `strategy: {type: Recreate}`. With one replica, the
  default `RollingUpdate` stalls: the new pod exits at start and restarts (crash loop) until
  the old one stops, which it never does while the rollout waits for the new pod.
* Connect directly, or through a pooler in session mode. A pooler in transaction mode
  (PgBouncer `pool_mode = transaction`) breaks the lock.
* {product} instances on different databases of one PostgreSQL server do not contend. Give
  {product} a database of its own: any role that can connect to it can take the same lock
  and keep {product} from starting.

== TLS in front of {product}

{product}'s listeners speak plain HTTP. In Kubernetes or the cloud an ingress or load
balancer usually terminates TLS already. Anywhere else, put a reverse proxy in front. With the
proxy on the same host, bind both listeners to loopback so nothing reaches {product} except
through it:

[source,toml]
----
[porth.http]
host = "127.0.0.1"

[porth.kannel]
host = "127.0.0.1"
----

A https://caddyserver.com[Caddy] `Caddyfile` for both listeners. Caddy gets and renews the
certificate for `sms.example.com` by itself:

----
sms.example.com {
	handle /api/v1/* {
		reverse_proxy 127.0.0.1:8080
	}
	handle {
		respond 404
	}
}

sms.example.com:13443 {
	reverse_proxy 127.0.0.1:13013
}
----

REST clients then call `https://sms.example.com/api/v1/sms/send`, and Kannel clients
`https://sms.example.com:13443/cgi-bin/sendsms`.

* Only `/api/v1` is published. `/health`, `/ready`, `/status`, `/metrics` and `/admin` need no
  token, so probe and scrape them on the host itself or over a private network. With loopback
  binding, a Prometheus on another host can't reach them.
* Behind a proxy, `allow_ip` sees only the proxy's address (see <<http-authentication>> and
  <<Authentication>>), and {product}'s logs show that address as the caller's. `allow_ip`
  then can't tell callers apart: a list without the proxy's address refuses every request,
  and one with it admits every request. Drop `allow_ip` and restrict callers at the proxy,
  or by network policy.
* Don't add Caddy's `log` directive to the Kannel site. Caddy's access log records the
  query string, and with it the Kannel password and any token in `dlr-url`. {product}'s own
  access log leaves the query string out.
* Loopback binding works only when the proxy runs on {product}'s host. With the container
  image keep `host = "0.0.0.0"` and publish the ports on loopback
  (`-p 127.0.0.1:8080:8080 -p 127.0.0.1:13013:13013`). In Kubernetes keep `0.0.0.0`, so the
  kubelet's probes reach the pod, and admit traffic only from the ingress (and from
  Prometheus, if it scrapes in-cluster) with a NetworkPolicy.
