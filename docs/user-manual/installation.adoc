= Installation and running

== Requirements

* Python 3.13 or later (pinned in `.python-version`).
* https://github.com/astral-sh/uv[uv].
* PostgreSQL 14 or later. `make db-up` starts one in Docker (`compose.yaml`, user, password and
  database all `porth`, on port 5432). To use another host port, set `POSTGRES_PORT` and
  change the port in the `db` DSN to match (see <<Configuration>>).
* Network access from {product} to the upstream SMSC's SMPP port.

{product} installs its SMPP library, `smppai`, from its Git repository. The library is
imported as `smpp`.

== Install

[source,bash]
----
git clone git@github.com:codcod/porth.git
cd porth
make dev        # uv sync --dev
make db-up      # PostgreSQL in Docker
make migrate    # create porth's tables (schema porth)
----

`make migrate` runs `alembic upgrade head` against the database in the `db` setting (see
<<Configuration>>). It is a one-off step: {product} never migrates at startup, so run it
again before every start after an upgrade. It reads `db` from `config/config.toml`.

== Run

[source,bash]
----
make run        # bin/porth config/config.toml
----

The gateway listens on the HTTP address from its configuration (default `0.0.0.0:8080`).
It starts even when an SMSC is unreachable, and retries the bind every 10 s (see
<<The SMSC bind>>). It does not
start without its database: an unset `db` or an unreachable PostgreSQL stops it with an
error.

Stop it with `SIGINT` (Ctrl+C) or `SIGTERM`. Shutdown first closes the HTTP API listener,
then stops the delivery workers, unbinds from the SMSC, and closes the Kannel listener.

== Try it without a carrier

`compose.demo.yaml`, in the repository root, runs {product} with its own PostgreSQL and
smppai's simulator SMSC (`python -m smpp.sim`). The simulator answers every message with a
delivery receipt and can send {product} an MO. It accepts any bind and has no
authentication, so use it only as a test tool. The file's header comment and the README's
*Try it* walk through a send, its status, and an MO:

[source,bash]
----
docker compose -f compose.demo.yaml up -d
----

* By default every receipt says `DELIVRD`, one second after the submit. To see failures too,
  change the `smsc` service's command to add `--stat DELIVRD:9 --stat UNDELIV:1` (about one
  message in ten, at random, comes back `failed`).
* The demo configuration sets no `mo.url`, so {product} logs each MO (`MO from <number>
  dropped: mo.url is not set`) instead of forwarding it. To forward MOs to an application,
  set `[porth.mo] url` in the `config.toml` entry at the end of the file.
* The demo uses `ghcr.io/codcod/porth:latest`, or builds it from the clone when it cannot be
  pulled. Until a release publishes that image, `up` prints a pull error (`denied`) and then
  builds: that is expected. Once an image is local, `up` keeps using it: after a `git pull`,
  add `--build`; after a new release, run `docker compose -f compose.demo.yaml pull` first.
  If `smsc` exits with `No module named smpp.sim`, the image predates the simulator: do the
  same.
* The demo publishes 8080 and 2776 on `127.0.0.1` only, since neither is authenticated (its
  config sets no `http.users`), and
  no database port. It shares nothing with `compose.yaml`, and `down -v` removes its database.

== Container image

Every release publishes the image `ghcr.io/codcod/porth:<version>` (for example
`ghcr.io/codcod/porth:0.3.0`), and `ghcr.io/codcod/porth:latest` names the most recently
tagged release.
It runs on `linux/amd64` and `linux/arm64`, and needs no Python or uv on the host. It is a
distroless Python 3.13 runtime holding `bin/porth`, the default `config/`, the migrations and
`alembic.ini`. It exposes 8080 (HTTP API) and 13013 (Kannel), and runs as a non-root user.

The image's entrypoint is `python`, so the same image runs the gateway and the one-off
migrate step. Mount the deployment's configuration over the default:

[source,bash]
----
docker run --rm -v /etc/porth/config.toml:/opt/porth/config/config.toml:ro \
  ghcr.io/codcod/porth:<version> -m alembic upgrade head
docker run -d --restart unless-stopped -p 8080:8080 -p 13013:13013 \
  -v /etc/porth/config.toml:/opt/porth/config/config.toml:ro ghcr.io/codcod/porth:<version>
----

The migrate step reads `db` from the mounted file, as `make migrate` does. Run it before
every start after an upgrade.

To build the image from a clone instead, run `make docker-build`. It builds the same
`Dockerfile` into the local image `porth`, which takes the place of
`ghcr.io/codcod/porth:<version>` in the commands above.

== What a restart keeps

Every message {product} accepts is written to PostgreSQL before the API answers, and every
status change after that. After a stop or a crash, the next start:

* sends the messages that were not sent yet (`pending` or `queued`, including those waiting
  to retry), oldest first. A message already `sent` is not sent again.
* still matches later delivery receipts to their messages.
* makes again any Kannel `dlr-url` or HTTP `callback_url` call that was not finished, so a
  client can receive the same callback twice.

A message the SMSC accepted just before a crash, before {product} recorded it as `sent`, is
sent again. See <<Limitations>>.

== Running more than one instance

One {product} runs per database. At start it takes a PostgreSQL advisory lock and holds it
until it stops. A second {product} on the same database exits with an error before it sends
anything:

----
RuntimeError: Another porth already uses this database (advisory lock 482906109032 is held): stop it first
----

Every 10 s, {product} checks that its database session, and with it the lock, is still alive.
A check that gets no answer within 10 s fails too. After a database restart or a dropped
connection, it logs an error and stops, because another {product} may hold the lock by then.
It exits with code 0, or with code 1 if its shutdown is still running 30 s later. Either
way its supervisor must restart it on any exit (Docker `--restart always` or
`unless-stopped`, systemd `Restart=always`), not only on failure.

If {product}'s host disappears without closing its connection (a lost node, a network
partition), PostgreSQL keeps that session, and the lock, for up to 30 s after its last check
before ending it; until then a new {product} exits at start. To free the lock at once, run
this connected to {product}'s database:

[source,sql]
----
SELECT pg_terminate_backend(pid) FROM pg_locks
WHERE locktype = 'advisory' AND classid = 112 AND objid = 1869771880 AND objsubid = 1
  AND database = (SELECT oid FROM pg_database WHERE datname = current_database());
----

* Kubernetes: set the Deployment's `strategy: {type: Recreate}`. With one replica, the
  default `RollingUpdate` stalls: the new pod exits at start and restarts (crash loop) until
  the old one stops, which it never does while the rollout waits for the new pod.
* Connect directly, or through a pooler in session mode. A pooler in transaction mode
  (PgBouncer `pool_mode = transaction`) breaks the lock.
* {product} instances on different databases of one PostgreSQL server do not contend. Give
  {product} a database of its own: any role that can connect to it can take the same lock
  and keep {product} from starting.
