= Limitations

{product}'s design commits to the following, but this release does not implement them yet.
The ticket reference identifies the planned change.

[cols="3,5,1",options="header"]
|===
| Area | Current behaviour | Planned

| Kannel-compatible `sendsms` API | `GET` only. Parameters beyond `to`, `from`, `text`,
`dlr-url`, `dlr-mask`, `smsc` and the credentials are ignored. Response codes are not yet Kannel's exact table. | POR-005
| Security | No TLS: the Kannel API's credentials travel in clear over HTTP, and an
`allow_ip` list is no substitute for a trusted network. The REST API has no authentication,
nor do its `/metrics`, `/status` and `/ready` endpoints: keep the HTTP listener on a trusted
network. | —
| Metrics | Counters start from zero at every restart. A final status whose database
write rolls back is still counted. | —
| SMSC routing | Kannel's `unified-prefix` and per-SMSC `allowed-prefix`, `denied-prefix`
and `preferred-prefix` lists are not supported. Rewrite the rules as one prefix table (see
<<Routing rules>>). | —
| Restart window | A message the SMSC accepted just before a crash, before {product}
recorded it as `sent`, is sent again. So is one {product} could not record as `sent` because
the database was unavailable for its retries (about 7 s); its receipts are also ignored. A receipt that arrives before {product} has recorded
its message as `sent` (an early part of a long message, or a very fast SMSC) waits in memory,
up to about 15 s; one still waiting at a crash is lost, and that message stays `sent`. | —
|===
