= Message delivery

== Lifecycle

. The API validates the request, builds a message, and queues it. The message is `queued`,
  and its status can be polled from now on.
. A delivery worker takes the message and sends it to the SMSC as one `submit_sm` per part.
  Text that fits one SMS is one part.
. When the SMSC accepts every part, the message becomes `sent`, and {product} records the
  SMSC's message id for each part, for receipt correlation.
. If the send fails, the message waits and is queued again. The first wait is
  `delivery.retry_delay` seconds, and each later one is `delivery.backoff_factor` times
  longer, up to `delivery.max_retry_delay`. Each message waits on its own, so one retry never
  holds up another. After `delivery.max_retries` attempts in total it ends `failed`.
. Some failures are permanent and end `failed` at once, with no retry: text needing more than
  255 parts, and an SMSC rejection of the message with a permanent error status. Of the SMSC's
  answers to a message, only four statuses are retried, as in Kannel: `ESME_RTHROTTLED`,
  `ESME_RMSGQFUL`, `ESME_RX_T_APPN` and `ESME_RSYSERR`. A timeout, a dropped connection, a
  refused bind, or `ESME_RINVBNDSTS` (the SMSC lost the session, so porth rebinds) is retried
  too.

. A delivery receipt from the SMSC then moves a `sent` message to `delivered`, `failed` or
  `expired`. See <<Delivery receipts>>.

A message becomes `delivered`, or `expired`, only from a delivery receipt.

== Routing

Each message is routed once, when it is submitted, and keeps its SMSC through every retry
and restart. <<Routing rules>> gives the rules.

* A number that nothing routes is refused at submit, and nothing is stored. The Kannel API
  drops it from a request with several numbers, and answers `403` only when none routes. The
  HTTP API answers `400`.
* A message is not routed again when its SMSC is slow or down: it waits for that SMSC, and
  retries there.
* At startup, an unsent message whose SMSC is no longer configured is routed again by the
  current rules, or ends `failed` if nothing routes it.
* Each SMSC has its own queue, its own `delivery.worker_count` workers and its own bind. A
  slow or unreachable SMSC holds up only its own messages.
* A reply to a mobile-originated message goes out through the SMSC the MO arrived on, not
  through the routing rules.

== Throughput cap

With an SMSC's `throughput` set, {product} sends it at most that many `submit_sm` PDUs in any
one-second window, across its workers together. Each SMSC has its own cap. Sends are spaced evenly, so there is no burst
after an idle spell. A concatenated message counts once per part, and its parts go out back
to back. A worker that would go over the cap waits for its turn. A worker that waited through
a rebind is still spaced when the bind comes up. The wait is not a failure and does not use up
a retry. An `ESME_RTHROTTLED` answer from the SMSC still goes through the normal retry path.

A message with more parts than the cap still goes out whole, and goes over the cap by its own
extra parts. The sends after it wait until the cap holds again.

A `high` priority message (see <<Send a message>>) leaves the queue first, but still waits
for its turn under the cap like any other. Each worker takes its next message off the queue
before it waits for its turn, so with a backlog a `high` message can still go out after up to
`delivery.worker_count` messages already taken, about `worker_count / throughput` seconds
(2 s with the default 10 workers at 5 per second). A lower `worker_count` on a throttled SMSC
shortens that.

{product} counts each message's parts at the moment its turn starts. The parts themselves go
out one after another, each once the SMSC has answered the one before, so a message's later
parts leave a little late. With a high cap and a slow SMSC, a second can carry a few more PDUs
than the cap. An `ESME_RTHROTTLED` answer from that edge is retried like any other.

== Encoding and length

{product} picks the SMPP `data_coding` for each message:

* **GSM 03.38 (`data_coding` 0)** when every character is in the GSM 7-bit alphabet or its
  extension table. One SMS holds 160 septets, and extension characters such as `€`, `[`,
  `]`, `{`, `}`, `~` and the backslash take two.
* **UCS-2 (`data_coding` 8)** otherwise. One SMS holds 70 characters, and a character outside
  the Basic Multilingual Plane, such as most emoji, takes two.

Longer text is sent as a concatenated SMS: several parts, each carrying a user data header
(UDH) that lets the handset reassemble them. The header takes room, so each part holds 153
GSM or 67 UCS-2 characters. An extension character is never split across two parts. A
message can have at most 255 parts.

== Addresses

{product} sets the SMPP type of number (TON) and numbering plan (NPI) from each address:

* `+` followed by digits goes out as international/ISDN, without the `+`.
* Plain digits go out as unknown/unknown.
* Anything else, such as `Porth`, goes out as an alphanumeric sender.

Spaces and `-` in numbers are ignored.

== The SMSC bind

{product} opens one transceiver bind to each configured SMSC. What follows holds for each
bind on its own.

* If the bind fails at startup, the gateway still starts and retries the bind every 10 s.
* A bind that is lost, or that the SMSC unbinds, is reopened within 10 s, even when nothing
  is being sent.
* When a send fails at the transport level (timeout, lost connection, not bound), {product}
  drops the bind. The next send, or the 10 s retry, opens a new one.
* An error *response* from the SMSC, such as an invalid destination or throttling, keeps the
  bind open. That message goes through the normal retry path.
* A send that times out is retried, even though the SMSC may already have accepted it. The
  recipient can then get the message twice.
* If one part of a long message fails, the whole message is retried, with every part sent
  again. The recipient may also see an incomplete fragment from the failed attempt.

== Delivery receipts

{product} asks the SMSC for a receipt (`registered_delivery = 1`) for every message. Each
receipt reports on one part, by the SMSC message id the SMSC returned for it, and moves the
message on as follows:

[cols="2,3",options="header"]
|===
| Receipt state | Message status

| `DELIVERED` | `delivered`, once every part has a `DELIVERED` receipt
| `UNDELIVERABLE`, `REJECTED`, `DELETED` | `failed`, on the first such part
| `EXPIRED` | `expired`, on the first such part
| `ENROUTE`, `ACCEPTED`, `UNKNOWN`, or none | unchanged, not a final outcome
|===

`delivered_at` is the time the last part's receipt arrived, in UTC. HTTP API clients see
the new status on their next poll. A message submitted with a `callback_url` also gets its
final status posted there, whatever set it (see <<Status callback>>). For a Kannel `dlr-url`
callback, see <<Delivery reports>>.

* A receipt is matched by the SMSC it arrived from and the exact SMSC message id, so two
  SMSCs that issue the same id never mix up their messages. A receipt whose id {product} does not
  know yet is looked up again for about 15 s, so a part's receipt that arrives before the
  later parts are submitted still counts. After that, it is logged at info and ignored. If
  every receipt is ignored, the SMSC reports ids in a different format from its `submit_sm`
  responses.
* A receipt for a message that is already `delivered`, `failed` or `expired` is ignored.
* Receipts arrive only while the bind is up. After a lost bind, the receipts the SMSC holds
  arrive once {product} rebinds, within 10 s.
* Receipts already received when {product} closes a bind are still applied.
* A receipt that arrives after a restart still reaches its message, since the SMSC message
  ids are kept in PostgreSQL with the message.
* Other inbound messages (mobile-originated SMS) go to the application. See
  <<Mobile-originated messages>>.
