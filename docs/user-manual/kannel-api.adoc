= Kannel-compatible API

{product} serves Kannel's `sendsms` interface on its own port, `kannel.port` (default `13013`,
the smsbox default). An existing Kannel HTTP client switches to {product} by changing only
the host it points at.

== Send a message

`GET /cgi-bin/sendsms` with query parameters:

[cols="2,1,4",options="header"]
|===
| Parameter | Required | Meaning

| `to` | yes | Recipient address. One recipient only: a space-separated list returns `400`.
| `text` | yes | Message text.
| `from` | yes | Sender address. {product} has no default sender.
| `dlr-url` | no | URL to fetch with the message's final outcome. See <<Delivery reports>>.
| `dlr-mask` | no | Which outcomes fetch `dlr-url`: `1` delivered, `2` not delivered, or
their sum. Without it, no callback is made.
| `username`, `password` | no | Accepted and ignored. The API has no authentication.
|===

Any other parameter is ignored. Any other method returns `405`. See <<Limitations>>.

[source,bash]
----
curl 'http://localhost:13013/cgi-bin/sendsms?username=u&password=p&to=%2B306900000000&from=porth&text=Hello'
----

A queued message returns `200` with a `text/plain` body:

----
0: Accepted for delivery
Message-ID: 3f1c…
----

`200` means the message was queued, not sent. A missing `to`, `from` or `text` returns `400` with
`3: Failed to send SMS: <reason>`.

== Delivery reports

When a delivery receipt settles a message (see <<Delivery receipts>>), {product}
fetches the message's `dlr-url` if `dlr-mask` includes the outcome:

[cols="1,1,3",options="header"]
|===
| Outcome | Bit | `%d`

| `delivered` | 1 | `1`
| `failed` or `expired` | 2 | `2`
|===

`dlr-mask` must be an integer. A missing or non-integer mask means no callback. The other
Kannel bits (4, 8, 16) are never produced yet (POR-005).

{product} replaces these escape codes in `dlr-url`, each URL-encoded:

[cols="1,4",options="header"]
|===
| Code | Value

| `%d` | The delivery report value from the table above.
| `%I` | {product}'s message id, as returned in `Message-ID`.
| `%F` | The SMSC message id of the part whose receipt settled the message.
| `%A` | The receipt text the SMSC sent.
| `%t` | The receipt's arrival time in UTC, as `YYYY-MM-DD HH:MM`.
| `%T` | The receipt's arrival time as a UNIX timestamp.
| `%%` | A literal `%`.
|===

Any other `%` code, such as `%p` or `%P`, is left as written. As in Kannel, a code is
replaced even when it is part of a percent-encoding, so write a literal `%` in `dlr-url` as
`%%` (for example `caf%%C3%%A9`).

* The callback is an HTTP `GET`. Any `2xx` answer is success.
* {product} makes up to 3 attempts, 1 s and then 2 s apart, each with a 10 s timeout, and then
  gives up.
* A callback still being attempted when {product} stops is made again after the next start,
  so the client can receive the same callback twice (as with Kannel).
* There is one callback per message, including a long message sent in several parts.
* There is no callback for a message that fails before the SMSC accepts it (POR-005).

[source,bash]
----
curl 'http://localhost:13013/cgi-bin/sendsms?to=%2B306900000000&from=porth&text=Hello&dlr-mask=3&dlr-url=http%3A%2F%2Fapp.example%2Fdlr%3Fid%3D%25I%26status%3D%25d'
----

== Mobile-originated messages

An SMS a subscriber sends to the service number arrives from the SMSC as a `deliver_sm`
(reassembled first if it came in parts). {product} forwards it to one application URL,
`mo.url`, which works like the `get-url` of a Kannel `sms-service`. With `mo.url` unset, each
MO is logged and dropped. See <<Configuration>>.

{product} replaces these escape codes in `mo.url`, each URL-encoded. The values are the ones
Kannel 1.4.5 sends:

[cols="1,4",options="header"]
|===
| Code | Value

| `%p` | The sender's number. A TON-international number has a leading `+`.
| `%P` | The number the MO was sent to, with the same `+` rule.
| `%k` | The first word of the text.
| `%r` | The words after the first, joined by single spaces.
| `%a` | All words, joined by single spaces.
| `%b` | The text as sent, spaces kept.
| `%t` | The MO's arrival time in UTC, as `YYYY-MM-DD HH:MM:SS`.
| `%T` | The MO's arrival time as a UNIX timestamp.
| `%c` | The text's coding: `0` (GSM text) or `2` (UCS-2).
| `%C` | The text's charset: `UTF-8` or `UTF-16BE`.
| `%%` | A literal `%`.
|===

Any other `%` code is left as written.

* GSM text reaches the application as UTF-8. UCS-2 text reaches it as raw UTF-16BE bytes, as
  in Kannel, so an application that takes UCS-2 MO must read `%C` (or `%c`) to decode it.
* Words are split on the bytes, as Kannel does. For UCS-2 each word except the last keeps a
  stray `00` byte, the high byte of the space. A character with a whitespace byte in it (`€`
  is `20 AC`) also splits a word, so `%k`, `%r` and `%a` may not decode as UTF-16BE: use `%b`
  for UCS-2 text.

.A `mo.url`
----
http://app.example/mo?from=%p&to=%P&text=%a&charset=%C
----

=== Replies

{product} fetches the URL once with `GET`, with a 30 s timeout. If the application answers
`200` or `202` with a `text/plain` body that is not empty once leading and trailing whitespace
is stripped, and `mo.reply` is on (the default), the stripped body is sent back to the MO's sender as an SMS from the number the MO was sent to. The reply is queued like
any other message, with no delivery report. A reply longer than one SMS is sent whole as a
concatenated SMS, where Kannel's default `max-messages = 1` sends only one.

Any other answer sends nothing and is logged: another status, another content type, or an
empty or whitespace-only body (where Kannel would send `<Empty reply from service provider>`). `mo.reply: false`
never sends a reply, like Kannel's `max-messages = 0`.

=== Delivery guarantee

Forwarding is at-most-once. A failed request (a connection error, a timeout, an error
status) is not retried. An MO whose request is still running when {product} stops is lost.
The MO itself is not stored.

Not supported: `post-url`, keywords (one URL takes every MO), and Kannel's `X-Kannel-*`
headers.
