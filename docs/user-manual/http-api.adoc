= HTTP API

[[http-authentication]]
== Bearer tokens

Each `[porth.http.users.<name>]` table is one caller of `/api/v1`, with its own token. See
<<HTTP users>>. A request to `/api/v1` must carry one of the tokens:

----
Authorization: Bearer <token>
----

and come from an address in that user's `allow_ip`, if it has one. Otherwise {product} answers
`401` with the header `WWW-Authenticate: Bearer realm="porth"` and the body
`{"error": "Unauthorized"}`, whichever check failed, and nothing is stored. The warning it logs
names the caller's address, never the token.

* With no users configured, `/api/v1` accepts any caller and {product} logs a warning at
  startup, as the Kannel API does.
* `/health`, `/ready`, `/status` and `/metrics` need no token, so probes and Prometheus can
  reach them. Keep them off the public network.
* The caller's address is the TCP peer. `X-Forwarded-For` is never read, so behind a proxy
  `allow_ip` sees the proxy's address.

== Send a message

`POST /api/v1/sms/send` with a JSON body:

[cols="2,1,4",options="header"]
|===
| Field | Required | Meaning

| `source_addr` (or `from_number`) | yes | Sender address.
| `destination_addr` (or `to_number`) | yes | Recipient address.
| `message_text` (or `message`) | yes | Message text.
| `priority` | no | `high` or `normal` (the default). See below.
| `callback_url` | no | An `http` or `https` URL with a host. {product} posts the message's
final status to it. See <<Status callback>>.
| `valid_until` | no | An RFC 3339 time with an offset, such as `2026-10-01T12:00:00Z` or
`2026-10-01T14:00:00+02:00`, in 2000 to 2099 in UTC. A message not yet sent by then
expires instead. See below.
| `keep_text` | no | `true` (the default) or `false`. With `false`, {product} blanks the
stored text once the message is `sent`, `failed` or `expired`. See below.
| `idempotency_key` | no | A string of 1 to 64 characters, with no NUL and no lone
surrogate, such as the client's request UUID. A repeat submit with the same key is answered
with the first message. See below.
|===

These bodies are rejected with `400`:

* one with any other field. A Kannel-style `dlr_url` is an unknown field too, so use
  `callback_url` instead.
* a `priority` other than `high` or `normal`.
* a `callback_url` that is not an `http` or `https` URL with a host.
* a `valid_until` that is not a time, has no offset, or is outside 2000 to 2099 in UTC.
* a `keep_text` that is not `true` or `false`.
* an `idempotency_key` that is not a string of 1 to 64 characters, or contains a NUL or a
  lone surrogate (`\ud800` to `\udfff`).

A `high` message leaves its SMSC's queue before every `normal` message waiting there, after a
restart too. Within a level, messages leave in the order they were accepted. Priority orders
only the queue of the SMSC the message is routed to, never another SMSC's. It does not skip
the throughput cap (see <<Throughput cap>>) or interrupt a send already under way, and a
retried message goes to the back of its level. A steady stream of `high` messages holds
`normal` ones back, so keep `high` for traffic that cannot wait, such as login codes.

A message still unsent at its `valid_until` becomes `expired` and is never sent. {product}
checks before each send and each retry, so a message whose `valid_until` passes while it
waits for a retry, a down SMSC's included, expires instead of being sent. It becomes `expired`
when that retry comes due, not at `valid_until` itself. Each failed attempt still counts
towards `delivery.max_retries`, so a message whose retries run out first ends `failed`. A
`valid_until` already past is accepted, and the message expires at its first send. The SMSC is told the same time as the `submit_sm` validity period, so it drops a
message it still holds by then. A message with a `callback_url` gets `expired` posted to it.

With `keep_text: false`, the stored text is blanked (set to an empty string) once the message
is `sent`, `failed` or `expired`. Until then it is kept, since a retry or a restart needs it.
Use it for text that must not be kept, such as login codes. {product} logs no message text.

A client that gets no answer to a submit cannot tell whether {product} took the message.
With an `idempotency_key`, it can safely submit again. A submit with a key {product} already
holds returns `200` with the first message's id and current status, and nothing new is sent:

[source,json]
----
{"message_id": "3f1c…", "status": "sent", "message": "Message already accepted"}
----

The repeat's other fields are validated as usual, and otherwise ignored, even if they differ
from the first submit's. Two submits with the same key at the same time get the same
`message_id`, and one message is sent. A key
lasts as long as its message, so for the retention window (see <<Lifecycle>>). After the
message is deleted, a submit with its key is a new message.

[source,bash]
----
curl -X POST http://localhost:8080/api/v1/sms/send \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: application/json' \
  -d '{"source_addr": "+1234567890", "destination_addr": "+0987654321",
       "message_text": "Hello from porth!"}'
----

A queued message returns `200`:

[source,json]
----
{"message_id": "3f1c…", "status": "queued", "message": "Message queued for delivery"}
----

`200` means the message was queued, not sent. A missing field, a malformed body, or a number
no SMSC takes (see <<Routing rules>>) returns `400` with `{"error": …, "details": …}`, and
nothing is stored. The HTTP API has no way to name the SMSC.

Two answers are `503`, and nothing is stored with either, so the submit is safe to repeat
(with the same `idempotency_key`, if it had one):

* The message store is unavailable: `{"error": "Failed to send SMS", "details": "message
  store unavailable"}`, with no `Retry-After` header.
* The SMSC the number routes to holds `delivery.queue_limit` messages, waiting or waiting to
  retry (twice that for a `high` message; see <<Settings>>): `{"error": "Failed to send SMS",
  "details": "queue full, try again later"}`, with `Retry-After: 10`. Submits to other SMSCs
  are still taken.

A client tells them apart by the `Retry-After` header.

== Status callback

A message submitted with a `callback_url` gets one `POST` to that URL when it reaches a final
status, so the client need not poll. The body is JSON:

[source,json]
----
{"message_id": "3f1c…", "status": "delivered", "occurred_at": "2026-09-26T10:39:12Z",
 "idempotency_key": "6b0e…"}
----

[cols="1,4",options="header"]
|===
| Field | Meaning

| `message_id` | The id the submit returned.
| `status` | `delivered`, `failed` or `expired`. `sent` is not reported.
| `occurred_at` | When {product} set the final status, in UTC, formatted `YYYY-MM-DDTHH:MM:SSZ`.
| `idempotency_key` | The submit's `idempotency_key`. Present only if the submit had one.
|===

* Every final status is reported, whatever set it: a delivery receipt, a send {product}
  gave up on (the SMSC rejected it, or every retry failed), at startup too, or no receipt
  within `store.dlr_timeout_hours` or a `valid_until` reached before sending (`expired`).
  See <<Message delivery>>.
* The URL has no escape codes, unlike a Kannel `dlr-url`: {product} adds nothing to it. The
  HTTP client may normalise its percent-encoding (`%41` is sent as `A`, a stray `%` as `%25`),
  which servers read the same way.
* Any `2xx` answer ends the call. Anything else, a redirect or a connection error included,
  is retried, waiting 2, 4, 8 … s between attempts (at most 300 s each), for
  `http.callback_retry_minutes` (5 by default: 8 attempts over about 4 minutes; see
  <<Settings>>). Then the call is given up and logged. A restart starts the window again. A
  redirect is not followed.
* The call is stored with the status, so a call cut short by a restart is made again when
  {product} starts. The client can therefore get the same status twice, and should treat a
  repeat as a no-op.
* Calls carry no signature. Since the URL is used as given, a receiver can tell {product}'s
  calls from others by a secret in it, such as
  `+https://app.example/sms/status?token=<secret>+`, and check the token itself. A hex
  token (`openssl rand -hex 32`) survives percent-normalisation unchanged. {product} stores
  the URL with the message, so anyone who can read its database sees the token. A call that
  goes through is logged by message id only, but a URL {product} can't call at all (a
  malformed one, such as a port above 65535) appears in full in the warning.

== Message status

`GET /api/v1/sms/status/{message_id}` returns `200`:

[source,json]
----
{"message_id": "3f1c…", "status": "sent", "created_at": "2026-09-26T10:39:09Z",
 "sent_at": "2026-09-26T10:39:10Z", "delivered_at": null}
----

[cols="1,4",options="header"]
|===
| Field | Meaning

| `status` | `queued`, `sent`, `delivered`, `failed` or `expired`. See <<Message delivery>>.
| `created_at` | When {product} accepted the message.
| `sent_at` | When the SMSC accepted the message, or `null`.
| `delivered_at` | When a delivery receipt reported it delivered, or `null`.
|===

Timestamps are UTC, formatted `YYYY-MM-DDTHH:MM:SSZ`. An unknown id returns `404` with
`{"error": "Message not found", "details": <message_id>}`. So does a finished message once
`store.retention_days` have passed since it was accepted (later while a status call is still
being made), because it has been deleted (see <<Lifecycle>>).

Messages sent through the Kannel-compatible API can be polled here too, by the `Message-ID`
that `sendsms` returned.

{product} keeps message records in its database, so a status survives a restart, until the
retention window deletes the record (see <<Lifecycle>>).

== Monitoring

Four endpoints on the HTTP API listener report on {product}. Unlike `/api/v1`, they need no
token (see <<http-authentication>>).

=== Health

`GET /health` is the liveness check. It returns `200` with `status`, the current
`queue_size` and `timestamp` (UTC, ISO 8601) while the process is up. It does not check the
SMSC bind.

=== Readiness

`GET /ready` returns `200 {"ready": true}` while every configured SMSC is bound (an SMSC
with `transceiver = false` counts as bound once both its binds are). While any is not, it
returns `503` and names them:

[source,json]
----
{"ready": false, "unbound": ["local"]}
----

=== Status

`GET /status` returns `200` with the version, the seconds since the HTTP API started, and,
per SMSC, whether it is bound, how many messages wait in its queue, and how many wait out
a retry:

[source,json]
----
{
  "version": "0.4.0",
  "uptime_seconds": 3600,
  "smsc": {"local": {"bound": true, "waiting": 0, "retrying": 2}}
}
----

=== Metrics

`GET /metrics` serves Prometheus metrics in the text exposition format. Besides the
standard `process_*` and `python_*` metrics, {product} exports:

[cols="3,1,2,4",options="header"]
|===
| Metric | Type | Labels | Meaning

| `porth_messages_submitted_total` | counter | `protocol` (`http`, `kannel`) | Messages
accepted for sending, one per recipient. Replies to MO are not counted.
| `porth_messages_final_total` | counter | `smsc`, `status` (`delivered`, `failed`,
`expired`) | Messages reaching a final status.
| `porth_send_retries_total` | counter | `smsc` | Retries scheduled after a failed send.
| `porth_smpp_errors_total` | counter | `smsc`, `command_status` | `submit_sm` errors, by
the SMSC's status name (for example `ESME_RTHROTTLED`).
| `porth_receipts_total` | counter | `smsc`, `matched` (`true`, `false`) | Delivery
receipts, matched to a message or given up on.
| `porth_mo_total` | counter | `smsc`, `result` (`forwarded`, `failed`) | MO forwarded to
the application, or whose request failed.
| `porth_messages_waiting` | gauge | `smsc` | Messages in the SMSC's queue.
| `porth_messages_retrying` | gauge | `smsc` | Messages waiting out a retry.
| `porth_smsc_bound` | gauge | `smsc` | `1` while the SMSC is bound (both binds, with
`transceiver = false`), else `0`.
| `porth_submit_seconds` | histogram | `smsc` | Time to submit a message to the SMSC,
after throughput pacing.
|===

A message whose SMSC was removed from the configuration, failed at startup, is counted in
`porth_messages_final_total` under its old SMSC name, or an empty one.

A minimal Prometheus scrape configuration:

[source,yaml]
----
scrape_configs:
  - job_name: porth
    static_configs:
      - targets: ["porth.internal:8080"]
----

The repository ships a Grafana dashboard and Prometheus alert rules for these metrics. To
use the dashboard, import `deploy/grafana/porth.json` into Grafana and pick your Prometheus
data source. Its `SMSC` variable filters the per-SMSC panels. For the alerts, add
`deploy/prometheus/alerts.yml` under `rule_files:`. The rules assume the `porth` job above,
and every rule over a counter uses `rate()`, because counters start from zero at every
restart.

[cols="1,1,3",options="header"]
|===
| Alert | Severity | Fires when

| `PorthDown` | critical | Prometheus has failed to scrape {product}, or has no target for
it, for 2 minutes.
| `PorthSmscUnbound` | critical | An SMSC has stayed unbound for 5 minutes.
| `PorthBacklogGrowing` | warning | Over 1000 messages are waiting or retrying for one
SMSC, and the number has kept rising for 15 minutes.
| `PorthFailedRatioHigh` | warning | Over 20% of an SMSC's final statuses in 15 minutes are
`failed`. An SMSC with fewer than 0.1 final statuses a second is ignored.
| `PorthReceiptsUnmatched` | warning | Over 5% of an SMSC's delivery receipts in 30 minutes
matched no message.
|===

The thresholds are starting points, so tune them to your traffic. If you set
`delivery.queue_limit`, keep the backlog threshold below it. {product} refuses submits at
the limit, so the backlog never grows past it and an alert set above it cannot fire.

Kubernetes-style probes:

[source,yaml]
----
livenessProbe:
  httpGet: {path: /health, port: 8080}
readinessProbe:
  httpGet: {path: /ready, port: 8080}
----

For the Deployment's strategy, see <<Running more than one instance>>.
